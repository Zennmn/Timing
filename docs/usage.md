# 使用说明

## 多首歌曲排队

每首歌选择音频、填写对应歌词并设置处理方式后，点“加入队列”。上传完成即可准备下一首；正在处理的任务使用提交时的歌词、音轨和设置，之后修改表单不会影响它。队列最多容纳 50 首未完成歌曲，按加入顺序逐首处理；某首失败后继续下一首。

队列只显示本次服务启动后提交的任务，包括已完成和失败的任务；刷新网页仍保留本次队列，不加载以前启动留下的历史记录。队列显示每首歌的处理状态、等待位置和下载入口。尚未开始的歌曲可以“取消排队”，已开始的歌曲会继续完成。关闭或重启本地服务会清空页面队列，并中断未完成任务，需要重新提交；已有结果文件仍保留在本机。接口 Key 不写入任务文件或浏览器存储。

TTML 下载文件名取自导入音乐，去掉音频扩展名再加 `.ttml`，例如 `歌名 (Live).flac` → `歌名 (Live).ttml`。歌曲名中的中文和标点会保留；已有任务也可按保存的歌名下载。

## 歌词和音轨

歌词为必填：填写正确歌词，或导入 UTF-8 TXT / LRC / JSON / 逐行 TTML。普通 TXT 每行一句；JSON 主歌词可省略时间。每行代表一次真实演唱；重复副歌要完整重复填写。LRC 示例：

```text
[00:01.20] 青い箱をひらく
[00:05.80] Paper lanterns drift away
```

LRC 也支持每行同时写开始和结束时间：

```text
[00:01.200]青い箱をひらく[00:04.800]
[00:05.800]Paper lanterns drift away[00:09.300]
```

`[开始]歌词[结束]` 会保留每句的明确范围，包括句间空白、重叠和最后一句结束；在歌词原文和起止范围上与逐行 TTML 相同。它可以和只有开始时间的行混用：缺少结束时间时，使用下一句起点，最后一句以音频结束为上限。单独的空白时间标签仍忽略。主歌词按开始时间排序；行尾必须晚于行首，范围不能超出音频。不支持把重复演唱的多个起点放在同一行，也不支持行内逐字时间标签，请展开为独立歌词行或使用 TTML / JSON。

带明确句段时间的 LRC / TTML / JSON 继续使用原有锚定窗口；只有开始标签的 LRC 仍按下一句起点或音频终点补齐结束。普通 TXT 每行一句；JSON 的 `main` 行可以省略 `start` / `end`，`auto` 与显式 `tifa` 都接受这种输入。带句段范围的歌词进入原生 TIFA 细对齐；无时间主歌词先由 MMS 做全曲声学定位，再把证据推导的窗口交给 TIFA。`ctc` 也接受无时间主歌词，并可从全曲 MMS 声学和全局有序 CTC 定位窗口，包括重复演唱。MMS-300M 的原生 20 ms 帧步进只是模型网格，不等于 20 ms 边界准确度；这些结果仍需试听校对。

```json
[
  {"text":"青い箱をひらく", "language":"ja"},
  {"text":"Paper lanterns drift away", "language":"en"}
]
```

无时间主歌词不按行数或时长平均分配时间；若某段文本无法由整曲声学证据定位，任务会明确失败，不会伪造锚点。细对齐中无法成立的单位也会在结果中明确记录，不用平均边界补齐。`ctc` 对纯文本和重复演唱使用全局有序定位。背景歌词（`role=bg`）即使在这些路线上也必须显式给出 `start` 和 `end`。歌词文件导入后填入文本框，提交以文本框为准。

纯文本按歌词顺序定位同一主唱的演唱；多位主唱的 JSON 请分别处理或提供逐句时间，以免把重叠人声强行排成先后顺序。未成为每帧第一候选、但仍有可用发音证据的句子会继续交给对应的本地声学路线，并标记为“整曲定位的发音证据较弱”；粗定位诊断分数和拒绝阈值都不是准确率。

逐行 TTML 可以直接导入 `.ttml` 文件或粘贴 XML；每个 `p` 的 `begin` / `end`（或 `begin` / `dur`）作为句段范围，最后一句明确的结束时间会保留。网页在本机将它转换为可编辑的 JSON，再沿用现有对齐和提示词流程；CLI / API 也可直接读取 TTML。已有逐字 `span` 会拼回整句，字时间由本次模型重新计算。

确信逐句时间准确时，可勾选“信任逐句时间轴，跳过 MMS 粗定位”（默认关闭）。适用于带时间的 LRC、转换后的 TTML 和带时间的 JSON；TTML 每句的开始、结束时间会保留。只有开始时间的 LRC 仍按下一句起点、最后一句按音频终点补齐结束。勾选后，TIFA 直接使用这些句段范围及原有上下文做细对齐，跳过 MMS 粗定位和据此寻找停顿的裁剪；逐字时间仍由 TIFA 计算。此选项适用于自动、TIFA 和三种 LLM + TIFA 路线，纯文本和 MMS 单独对齐时不可用。每首歌入队时保存自己的选项。CLI 对应 `--trust-line-timestamps`，API 对应布尔字段 `trust_line_timestamps`。

```xml
<tt xmlns="http://www.w3.org/ns/ttml">
  <body><div>
    <p begin="00:00:01.200" end="00:00:04.800">Paper lanterns</p>
    <p begin="00:00:05.800" end="00:00:09.300">drift away</p>
  </div></body>
</tt>
```

支持歌曲绝对时间的时分秒、分秒、秒数及 `h/m/s/ms` 表达式；AMLL `div` 的时间只做包含范围检查，不叠加到歌词时间。支持内联的 `x-translation` 翻译、`x-roman` 罗马音和 `x-bg` 伴唱；伴唱缺少独立时间时沿用该句范围。Apple 在 `head` 的 `iTunesMetadata` 内存放的 `translations` / `transliterations` 通过 `text for="L1"` 等标记关联 `p` 的 `itunes:key`；每句有多轨 sidecar 翻译时固定取关联轨道中的第一份，不按中文或其他语言偏好选择。TTML 的根节点、行和伴唱 `xml:lang` 声明全部忽略，不继承到行级；这些声明可能错误，不作为对齐、字典或 LLM 输入。本地 TIFA / MMS 仍使用用户手选的语言，LLM 路线则自行判断。`v1` / `v2` / `v3` / `v1000` 等演唱者 ID 会保留，其他命名映射为可用的 `vN`。没有 `itunes:key` 且没有关联翻译的逐行文件也可以读取。

当前每句保留一份翻译和一份罗马音；多份内联标注、重复或无效的关联行 ID、未知角色、嵌套伴唱、DTD / 实体、帧 / tick / SMPTE 时间、`seq` 容器和带 `begin/end` 的 `body` 会明确报错。TTML 的排版样式、演唱者姓名 / person 或 group 类型和其他歌曲元数据不作为对齐输入；普通 XML 空白按规则折叠，`xml:space="preserve"` 可保留句内空白。歌词文件上限为 2 MB，导入后可在 JSON 中检查句段和声部。

音频预处理三选一：

- 只保留主唱（默认）：用 BS-Roformer 去掉伴奏，并尽量去掉和声；输入可以是原曲，也可以是导入的主唱 / 人声轨。
- 保留全部人声：用 Kim 去掉伴奏、保留主唱和和声；已导入人声时直接使用导入轨。
- 直接使用所选音轨：不改动原曲或导入轨。

导入的音轨必须与原曲同起点、同时长。分离失败会报错，不会静默改用其他轨。所有模式共用同一套四组本地模型，安装后没有按功能补装步骤；缺项时页面会提示补装命令。SOFA 不再下载或要求，旧 `models/sofa/` 缓存也不会被读取。

## 本地对齐的语言选择与后端

用于本地对齐的网页“歌曲语言”与 CLI `--language` 使用同一组取值：

| 取值 | 含义 |
| --- | --- |
| `mixed` | 默认；日语 / 英语 / 日英混唱 |
| `ja` / `en` | 日语 / 英语 |
| `zh` | 中文（普通话） |
| `zh-en` | 中英混唱 |
| `auto` | 仅用于 JSON 行级，表示继承整首选择 |

本地方案无法仅凭汉字区分中文与日语：只有整首或该行选择 `zh` / `zh-en` 时，汉字才按普通话处理；其他模式沿用日语读法。中文指普通话，不处理粤语。行级 `language` 只用于本地方案。所有 LLM 对齐路线（`llm_text`、`llm_direct`、`llm_import`）不提供语言选择，也不发送整首或行级语言提示；模型自行判断每段语言，返回片段必须保留 `lang`。

```powershell
.\.venv\Scripts\python.exe -X utf8 -m timing "song.flac" --lyrics "song.lrc" --output "song.ttml" --language mixed
```

| 参数 | 用途 |
| --- | --- |
| `--lyrics` | 必填；UTF-8 TXT / LRC / JSON / 逐行 TTML |
| `--aligner auto` | 默认；带句段范围时使用 TIFA，无时间主歌词先由 MMS 粗定位再交给 TIFA；接受普通 TXT / 无时间 JSON 主歌词或带逐句范围的 LRC / TTML / JSON |
| `--aligner tifa` | 使用 TIFA 细对齐；无时间主歌词仍先由 MMS 粗定位；歌词格式和定位流程与 `auto` 相同 |
| `--aligner ctc` | MMS 逐句或整曲 CTC 对齐；0.20.0 接受锚定歌词以及无时间 TXT / JSON |
| `--aligner llm_text` | 读取整首歌词文字，由模型推断每段语言、上下文读音和分段；不发送音频、时间或语言预设，随后在本地计时；需逐句 LRC / TTML / JSON |
| `--aligner llm_direct` | 一次发送完整音轨和歌词，由模型自行判断每段语言、读音和拆分；不发送语言预设，需逐句范围与音频兼容接口 |
| `--aligner llm_import --llm-result result.json` | 使用网页 LLM 返回的 JSON，不请求接口，不需要 Key；提示词不含语言预设，输入仍需逐句范围 |
| `--export-llm-prompt prompt.txt` | 将全部歌词和不含语言预设的输出规则写入提示词 TXT 后退出；需要带句段范围的 `--lyrics` |
| `--llm-prompt-profile fine` / `original` | 整曲音频 API 和网页提示词的日语拆分规则；默认 `fine` 细拆，`original` 保留适度合并的旧版；`llm_text` 使用固定文本提示词，不受此参数影响 |
| `--audio-mode lead` | 默认；去掉伴奏、尽量去掉和声（BS） |
| `--audio-mode vocals` | 去掉伴奏、保留主唱和和声（Kim） |
| `--audio-mode source` | 直接使用原曲或导入轨 |
| `--vocals vocals.wav` | 导入同起点同时长的人声 / 原声轨 |
| `--word-level` | 英语保留整词，不细分候选音节 |
| `--english-splitter syllabify` / `pyphen` / `llm` | 英语候选音节方案 |
| `--language mixed` / `ja` / `en` / `zh` / `zh-en` | 本地整首语言；默认 `mixed` 覆盖日语 / 英语 / 日英混唱，`zh` 为普通话，`zh-en` 为中英混唱；LLM 对齐不使用此参数 |

本地 `--language` 决定文字处理：`zh` / `zh-en` 时汉字按普通话（拼音）处理，其余模式汉字按日语读法。`llm_text` 与 `llm_direct` / `llm_import` 一样，由模型推断每段语言；手选语言、JSON 行级 `language` 和 TTML `xml:lang` 都不作为请求提示，也不约束本地回退。返回片段的 `lang` 是模型结果。源文件、歌词和输出路径不能相互覆盖。CLI 中间输出保存在 `<输出文件名>.timing/`。

本地中英混唱示例：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m timing "song.flac" --lyrics "song.lrc" --output "song.ttml" --language zh-en
```

## 伴唱、对唱和重叠

用 JSON 明确每行范围及对应关系；以下均为演示文本：

```json
[
  {"text":"青い箱", "start":10.0, "end":15.0, "agent":"v1", "language":"ja"},
  {"text":"paper lantern", "start":14.0, "end":19.0, "agent":"v2", "language":"en"},
  {"text":"ah", "start":12.0, "end":15.0, "role":"bg", "parent":0}
]
```

`parent` 是主歌词行从 0 开始的下标；`agent` 为 `v1`、`v2`、`v3` 等正整数演唱者 ID（最多 9 位数字），`role` 为 `main` / `bg`。可附加 `translation` 和 `roman`。行级 `language` 接受 `auto` / `mixed` / `ja` / `en` / `zh` / `zh-en`，供本地文字处理使用，显式值优先于整首 `--language`；`zh` 为普通话。例如中文行写 `{"text":"今天很好","start":10.0,"end":13.0,"language":"zh"}`，英文行写 `"language":"en"`。LLM 对齐模式不读取或发送这些预设。显式结构不代表模型自动识别或分离不同歌手。

背景歌词（`role=bg`）在“只保留主唱”模式下对齐到 Kim 提取的完整人声，或导入的完整人声；没有原曲回退，也不能把“原曲减主唱”的剩余轨当作纯伴唱。“保留全部人声”和“直接使用所选音轨”模式使用该模式选定的音轨。

## 读音与候选音节

在 `dictionaries/pronunciations.json` 中填 `ja`（词到假名字符串）、`en`（词到音素数组）和 `zh`（汉字或词组到拼音）。例如 `"zh": {"重": "chong2", "重庆": "chong2 qing4"}`；词组需每字一个音节，单字设置优先。TIFA、MMS 和本地文本路径使用这些设置，共享读音 / 音素辅助使用 TIFA 资源；`llm_text` 的成功行使用模型返回的读音，失败行才尝试人工覆盖和中性脚本回退：出现明确假名时按日语处理，无假名且不含汉字的拉丁文字按英语处理；含汉字但无假名、无法消解中日语歧义时保留给人工处理并标注回退。`llm_direct` / `llm_import` 使用听音模型返回的读音。拼音可带声调数字或声调符号，字典匹配时会去掉声调。不修改原文或制造时间。表中整数提供读音候选，特殊年份 / 编号仍应校对。中文按普通话处理：TIFA 使用原生中文音素词典，MMS 使用无调拼音标签；不覆盖粤语。词典不支持的唱法会明确报错，可指定受支持的读音后重试。

### LLM 文本读音（不听音）

`--aligner llm_text` 把词库查询替换为一次整首歌词的文字调用。本版沿用逐句定位流程，需要带逐句开始和结束时间的 LRC、逐行 TTML 或完整 JSON。请求只包含歌词原文、稳定行 ID、不含语言预设的固定输出规则和允许音素，不包含音频、音频片段、文件名、标题、翻译、整首或行级语言提示、演唱者关系、角色、之前测出的时间或时间戳。模型像 `llm_direct` / `llm_import` 一样自行判断每段语言、读音和分段。行 ID 用于保证重复副歌的每次演唱分别返回，不会把相同文字的出现合并。

应用按行校验返回结果：每个 ID 恰好出现一次，每个分段字段只允许 `text` / `lang` / `reading`，且 `lang` 必须存在，因为它是模型输出；所有 `text` 拼接必须与对应歌词逐字符完全相同，保持空格、标点、大小写和重复文字。读音分别使用日语片假名、普通话拼音或无调英语音素。单行不合法、漏行或重复行时，只让该行尝试人工读音覆盖和中性脚本回退：明确假名启用日语，无假名且不含汉字的拉丁文字启用英语，含汉字但无假名的歧义保留给人工处理，不读取 `--language`、JSON 行级语言或隐藏默认值。回退在 `llm_text.json` 和任务报告中逐行标注；若本地回退也不可用，该行标记为人工待补轴并保留锚定的整句范围。整次请求失败时各行执行同一回退。成功和失败都不调用第二次模型请求。

文本模型的固定提示词要求根据整首上下文选择读音，同时明确没有听到音频，不能声称识别音高、时长或时间戳。提示词只包含中日英读音所需规则和允许音素，不使用“细拆 / 适度合并”模板选择。完成校验后交给本地 TIFA 计时。形态合格只表示文字、读音和分段结构通过检查，不代表演唱读音或边界已经正确。

日语提示词要求 LLM 先结合整首歌词的词义、形态和语法确定读音与文字对应，再判断自然分块；既不把依赖的小假名、促音或鼻音单独高亮，也不把本可独立的词或短语无必要地整段合并。听音模式以实际人声的发音、重新起音和连续性为首要证据，词义和语法帮助绑定文字；确有独立重新起音或单独发音的鼻音可以拆开，仅音高变化或拖音本身不足以拆分。小假名组合不拆，促音 `っ/ッ` 优先并入前一块，延长同一元音的 `う/い/ー` 等与前面的发音合并；鼻音 `ん/ン` 正常也依附前一块，如 `カバン → カ/バン`、`押し込んだ → 押/し/込ん/だ`。例如 `ありがとう` 拆为 `あ / り / が / とう`，`さようなら` 拆为 `さ / よう / な / ら`，`いって` 拆为 `いっ / て`。合并块保留完整的鼻音、闭塞和长音元音长度，不删音素；鼻音仍是实际发声的莫拉，不能当作静音。真正独立的元音如 `買う` 的 `う` 不机械合并。文本模式只能依据词义和语法判断，不能听出实际重新发音。这些组合优先于拖音和句尾的一般细拆要求，已返回的 LLM 分块会原样用于本地对齐和 TTML 显示。

本地日语路线用 Fugashi / MeCab 读取 `models/unidic-cwj-202512/` 中的 UniDic CWJ 202512（ver.2025.12）常规分析包，负责日语分词和读音基线；普通文本、TIFA 与 MMS 的本地路径共用这套文字处理。它是静态词库，不是需要训练的对齐模型，安装时会显式下载并核对文件哈希，运行任务时不会联网补词。TIFA 模型目录里的 `japanese_dict_full.txt` 只是假名到音素的映射表，不能拿它替代分词词典。旧版 `models/unidic-cwj-3.1.0/` 若仍留在本机，只作为已完成下载缓存，当前运行路径不读取它。

`dictionaries/pronunciations.json` 的日语覆盖仍用于歌词特殊读法、多音字或人工确认的唱法；唱法没有支持的音素时仍会报错。LLM 文本读音成功采用的行不查询本地 UniDic；失败行才执行人工覆盖和上述中性脚本回退，含汉字但无假名的歧义留给人工处理。听音整曲与网页 LLM 导入始终使用返回结果里的读音和分段。任何词典升级都不是“日语读音一定更准”的保证，也不能解决脱离上下文的异读或实际演唱变音。

`syllabify` 使用选中的音素，`pyphen` 使用拼写候选，`llm` 把去重后的英语单词和已选音素作为文字发给兼容接口，再检查返回分段是否连续覆盖这些音素。英语 LLM 拆分不发送音频，也不产生时间。英语边界按声音优先处理：听音路线从实际人声确定音节和辅音归属，`llm_text` 从上下文确定规范读音，`syllabify` / `llm` 从已提供音素确定，之后才映射回原词字母；词根、词缀或拼写不覆盖声音。`pyphen` 只是拼写候选，不能把它的切分当作发音证据。细分边界不确定时保留整词，书面词界始终保留。例如仅当音频或音素确为 `w ao | k ih ng` 时，`walking` 才显示为 `wal/king`；没有把所有辅音一律划给后一音节的规则。无法安全映射时保留整词。连续元音或一个不可分读音可以作为整体，不按字数平均分配时间。方案记录在 `alignment.json`，结构正确不等于实际唱法正确。

## 网页 LLM 导入

整曲音频 API 和网页提示词有“日语拆分”选择：**细拆（默认）**要求日语全曲以最小自然且有据可依的独立单位为基本显示单元；**适度合并（旧版）**保留原有的连贯段落语义，但仍须隔离演唱中独立突出的单位，不能因整句流畅而不拆。两版都先依据整首词义、形态和语法判断，避免把依赖的声音单独高亮，也避免把可独立词句无必要地整段合并，并共用小假名、促音、真长音和鼻音附前规则：`とう`、`よう` 的延长元音或 `っ` 不单独切出，`カバン` 显示为 `カ/バン`，`押し込んだ` 显示为 `押/し/込ん/だ`。鼻音 `ん/ン` 仍是保留完整音素和时值的发声莫拉；独立重新起音或实际单独发音时可以拆开，仅音高变化或拖音本身不要求独立。两份模板独立保留，英语统一要求逐词分开，词内可按演唱需要拆音节，禁止把半个词与相邻单词合并；中文规则不变。“LLM 文本读音”使用另一份固定提示词，不显示也不读取这个选项。新 API 与文本任务读取更新后的提示词；网页提示词更新或切换后需重新生成并让模型返回新结果，质量仍需试听检查。已导入 JSON 始终采用它实际返回的分段。CLI 选择旧版可加 `--llm-prompt-profile original`。

只有网页端的音频模型也能使用，应用不需要它的 API：

1. 填写逐句 LRC、导入逐行 TTML 或使用带完整时间的 JSON，选择“网页 LLM（导入结果）”。生成提示词，然后复制或下载。提示词已经包含全部歌词、每次演唱的行 ID、英语可用音素和输出格式，但不含歌曲或行级语言预设。
2. 在模型网页上传同一首完整录音，粘贴提示词。保留前奏、间奏、尾奏及原始起点；有和声歌词时，上传的录音要包含和声。也可上传与原曲同起点、同时长的完整人声轨。
3. 将返回的完整 JSON 粘贴回来，或导入 UTF-8 JSON 文件。可以先点“检查结果”，再生成 TTML。所有检查和计时都在本机进行，不请求 LLM，也不会用另一个接口修正结果。

返回的每段包含 `text`、`lang`、`reading`，由网页模型自行决定中文 / 日语 / 英语语言、读音及显示分段。`lang` 是模型输出，不是预设提示。读取结果后由本地 TIFA 计算具体时间；中日英混唱也不需手选语言。

结果必须包含 `request_id` 和全部行 ID；`parts` 拼接须与原歌词完全相同，不接受生成的时间、改写文字、漏行、重复 ID 或不支持的读音。某行听不清可明确返回 `parts:[]`，该行会保留整句 LRC 范围供人工补轴。格式错误会在分离和计时前说明行号，修好后再导入。歌词或逐句范围改变后需重新生成提示词；相同歌词结果可用于对比不同本地音轨，绑定标识不验证音频内容。JSON 文件上限 16 MiB。提示词和导入结果不保存到浏览器存储，任务报告会保存实际采用的拆分与读音。

命令行两步使用，无需接口配置：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m timing --lyrics song.lrc --export-llm-prompt prompt.txt
.\.venv\Scripts\python.exe -X utf8 -m timing song.flac --lyrics song.lrc --aligner llm_import --llm-result result.json --output song.ttml
```

## 可选 LLM 接口

在页面填写 Base URL、模型 ID 和 Key。接口采用 Chat Completions；默认不强制 JSON 模式或采样参数。可自定义 Key 头名称和 `auto` / `bearer` / `raw` 发送格式。`Authorization` 在自动格式下加 Bearer，其他头默认原样发送。

- 英语 LLM 拆分（`--english-splitter llm`）：配合 TIFA 等本地路线，按任务去重后只发送英语文字与已选音素，保持原字母和音素连续对应，不发送音频，不产生时间。
- `--aligner llm_text`：整首上下文文本读音，发送歌词文字、稳定行 ID、不含语言预设的固定输出规则和允许音素；不发送音频、音频片段、整首或行级语言提示、演唱者关系、时间和时间戳。模型自行判断并返回每段 `lang`、读音和拆分；失败行按前述中性脚本规则回退，不自动补发请求。
- `--aligner llm_direct`：一次发送完整音轨和全部歌词，模型自行判断每段中日英语言、实际读音及拆分；同一句中也能混用这些语言。不使用手选语言、行级语言提示、本地词语读音和英语拆分开关。仍需完整逐句 LRC / TTML / JSON，歌词不改写。

整曲识别不再按 8 行 / 45 秒分批，也不自动修正请求。接口超时、输出截断或格式错误不会自动重发；可用行继续对齐，缺漏或无效的行保留整句 LRC 范围，标为待补轴。一次请求读取超时为 600 秒；完整音轨编码成 16 kHz 单声道 PCM WAV，不删前奏、间奏和尾奏，保留原曲时间线。仅主歌词时发送所选处理轨；有背景歌词时发送同时含主唱和和声的完整人声轨（直接使用音轨模式则沿用所选轨），本地计时仍分别使用对应音轨。

整曲音频识别和网页提示词的远端处理会接触完整录音；`llm_text` 和英语文字拆分不会。普通 5 分钟音轨的 WAV 约 9.2 MiB，Base64 约 12.2 MiB。整曲音频应用对编码音频设有 64 MiB 的本地上限，整曲响应上限为 16 MiB；音频超出本地上限时不发送请求，保留整句时间供手工补轴。接口自己的大小、时长、输入格式和输出长度限制可能更严格。请选能接受整曲输入、足够长 JSON 输出的音频模型；应用不会因接口拒绝而偷偷改成逐句多次请求。

音频使用 `messages[].content[].input_audio.data` 中的 WAV data URL。只有文字接口兼容不代表支持此音频格式；固定词测试也不能验证音频能力。远端服务的可用性和质量需自行确认。

API Key 通过页面或 `TIMING_LLM_API_KEY` 环境变量提供；不要写入源码或命令参数。CLI 连接参数示例：

```text
--english-splitter llm --llm-base-url https://provider.example/v1 --llm-model MODEL_ID
--llm-api-key-header x-api-key --llm-api-key-format raw
```

环境变量还支持 `TIMING_LLM_BASE_URL`、`TIMING_LLM_MODEL`、`TIMING_LLM_JSON_MODE`、`TIMING_LLM_API_KEY_HEADER`、`TIMING_LLM_API_KEY_FORMAT`。没有自动加载 `.env` 的功能；请在当前终端中设置环境变量。

思考参数可选跟随平台 / 开启 / 关闭。跟随平台不发额外参数；开启时选择 `reasoning_effort`、`enable_thinking` 或 `thinking` 格式，按接口文档填写强度。后两种格式需要纯开关时留空强度。CLI 支持 `--llm-thinking-mode`、`--llm-thinking-format`、`--llm-reasoning-effort`，对应环境变量前缀 `TIMING_LLM_`。参数不匹配会报错，不会静默删掉重试。

提示词在 `timing/prompts/`。对齐记录保存实际映射、请求数、参数和回退原因；LLM 报告同时记录 `language_hints_sent=false`，不保存 Key、音频 Base64 或思考正文。读音和拆分校验只说明映射结构合格，不证明时间更准确。

## 结果和恢复

下载 TTML、JSON 报告及本次分离产生的音轨。主唱提取的剩余轨包含伴奏和和声，只供试听；背景歌词使用 Kim 完整人声或导入的完整人声，不使用剩余轨。分离后的采样点和重建检查只验证时间线完整性。

`partial_timing_lines` 列出需补轴的单位，`manual_timing_lines` 列出整句占位，`export_placeholders` 记录带输入句段范围路线的 TTML 零时长编辑标记。保留的有效单位仍使用模型原生边界；标记不能视作已测量的字时长。无时间主歌词若无法定位会明确失败，不用这些占位符代替声学锚点。

页面刷新可恢复最近任务的查询；应用重启会将尚未结束的任务标为中断，需重新提交。进度持久化对短暂文件占用有重试和恢复副本；若整个目录不可写，结果写入仍可能失败。数据在 `data/`，不会自动上传或清理。
